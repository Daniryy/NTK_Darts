# Oche: сервер — запуск и обслуживание

Node.js 22 + Fastify + PostgreSQL 16. Логика сетки и упражнений общая со страницей: `shared/bracket.js` и `shared/games.js`.

```
server/            код сервера (routes/ — запросы из docs/api.md)
db/migrations/     схема базы, файлы применяются по порядку
db/seed.js         демо-данные как на странице
shared/            модули сетки и упражнений (общие со страницей)
test/              тесты API на настоящей базе
deploy/            установка и обслуживание VPS
```

## Локально

1. Нужны Node.js 22 и Docker (или своя PostgreSQL 16).
2. Установить и заполнить:
   ```
   docker compose up -d        # база oche и тестовая oche_test
   cp .env.example .env
   npm ci
   npm run seed                # схема + демо-данные
   npm run dev                 # http://localhost:3000 — страница и API
   ```
3. **Вход без VK** (только не в production): `POST /api/auth/dev` с телом `{ "playerId": "p17" }`. p17 — «Тестовый Игрок», это «Вы» из демо. Он организует идущий «Кубок Лиги · этап 4» и «Ночной турнир».
4. Пересоздать демо-базу: `npm run seed -- --reset`.
5. Тесты: `npm test`. Тестовая база стирается целиком, имя должно содержать `test`.

## Настройки (переменные окружения)

| Переменная | Что это |
|---|---|
| `DATABASE_URL` | адрес базы |
| `PORT` | порт сервера (3000) |
| `NODE_ENV` | `production` на VPS: выключает вход для разработки и раздачу страницы сервером |
| `COOKIE_SECRET` | случайная строка для подписи cookie, в production обязательна |
| `PUBLIC_URL` | адрес сайта, например `https://oche.ru`: для возврата из VK и защищённых cookie |
| `VK_APP_ID` | ID приложения VK ID |
| `SMS_PROVIDER` | вход по телефону: `smsru` (на VPS) или `log` — код только в журнал (по умолчанию в разработке) |
| `SMS_METHOD` | `call` — звонок-сброс, по умолчанию (в разы дешевле SMS) или `sms` |
| `SMS_RU_API_ID`, `SMS_FROM` | ключ sms.ru и имя отправителя (если согласовано в sms.ru) |
| `SMS_DAY_MAX` | звонков или SMS за сутки на весь сервер (300): защита от большого счёта |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS` | почта для кодов: регистрация, привязка почты, новый пароль (порт 465 — SSL, 587 — STARTTLS) |
| `MAIL_FROM` | адрес отправителя (по умолчанию `SMTP_USER`) |
| `MAIL_DAY_MAX` | писем за сутки на весь сервер (500) |
| `TELEGRAM_TOKEN`, `TELEGRAM_CHAT` | оповещения о сбоях |
| `RATE_MAX` | запросов за 2 с с одного устройства (20) |
| `UPLOAD_DIR` | куда класть фото (на VPS `/srv/oche/uploads`, локально `uploads/` в репозитории) |
| `CONTACT_EMAIL` | почта для вопросов о личных данных: показывается на странице «Политика обработки персональных данных» (`#privacy`) |
| `PRIVATE_DIR` | документы заявок на звания (на VPS `/srv/oche/private`, локально `uploads-private/`); nginx эту папку не отдаёт |

## Регистрация и почта

Игроки регистрируются сами: «Войти» → «Почта» → «Зарегистрироваться» (имя, город, почта, пароль от 8 символов). На почту приходит код из 6 цифр — после него аккаунт готов. Дальше вход по почте и паролю; «Забыли пароль?» присылает код для нового пароля. Уже заведённые аккаунты (по коду от ведущего, телефону, VK) привязывают почту в профиле: «Вход в аккаунт» → «Почта» → «Привязать», затем задают пароль. Администраторам панель напоминает подтвердить почту или телефон: через них восстанавливается доступ.

**Без настроенной почты** регистрация тоже работает, но адрес не подтверждается и «Забыли пароль?» не появляется. Чтобы письма уходили — подойдёт обычный ящик:

1. Завести ящик для сайта, например на Яндексе (`oche.darts@yandex.ru`).
2. Яндекс ID → «Безопасность» → «Пароли приложений» → создать пароль для «Почта». В настройках почты Яндекса («Почтовые программы») включить доступ по протоколу IMAP — иначе Яндекс не даст отправлять. Для Mail.ru: «Безопасность» → «Пароли для внешних приложений», сервер `smtp.mail.ru`.
3. На сервере (от root):
```
bash /srv/oche/app/deploy/set.sh SMTP_HOST=smtp.yandex.ru SMTP_USER=oche.darts@yandex.ru SMTP_PASS=пароль_приложения
bash /srv/oche/app/deploy/mailtest.sh ваш@адрес.ру
```
`mailtest.sh` проверит, открыты ли порты 465 и 587, примет ли SMTP пароль, и отправит тестовое письмо. Если хостинг закрыл порт 465, а 587 открыт — `set.sh SMTP_PORT=587`. Если закрыты оба — попросить поддержку хостинга открыть исходящие 465 и 587.

`set.sh` без аргументов показывает настройки (пароли скрыты); с аргументами `КЛЮЧ=значение` меняет их в `/etc/oche.env` и перезапускает сервер. Значения — без пробелов и кавычек.

Защита: код действует 30 минут, 5 попыток; письмо на адрес не чаще раза в минуту и 5 в час, 10 в час с устройства, `MAIL_DAY_MAX` в сутки на сервер; регистраций с одного IP — 300 в час; 5 неверных паролей к аккаунту с одного адреса — пауза 15 минут (снимается новым паролем по письму), подробно — docs/api.md, «Лимиты входа». Ответ «Забыли пароль?» одинаковый для любых адресов — по нему не узнать, есть ли аккаунт.

## Вход по телефону (звонок-сброс)

По умолчанию код приходит звонком-сбросом: sms.ru звонит с номера, последние 4 цифры которого — код; отвечать не нужно. Это в разы дешевле SMS. SMS (`SMS_METHOD=sms`) — запасной вариант.

1. Зарегистрироваться на sms.ru, пополнить баланс, проверить тариф «Авторизация по звонку».
2. В личном кабинете взять `api_id`.
3. На сервере: `bash /srv/oche/app/deploy/set.sh SMS_PROVIDER=smsru SMS_RU_API_ID=…`.
4. Проверить вход по своему номеру.

Без этих настроек на странице нет вкладки «Телефон» — остаются почта, VK и код от ведущего (бесплатно). Ограничения: код раз в минуту и не больше 5 в час на номер, 10 в час с устройства, `SMS_DAY_MAX` за сутки на сервер.

## Роли и вход администраторов

Игрок → ведущий (клуб подтверждён) → администратор (заказчик) → тех. администратор (разработчики). Ведущих назначает администратор: подтверждает заявку клуба в «Панели управления» (щит в верхней панели). Администраторов назначает тех. администратор там же. Что может каждая роль, тех. администратор настраивает во вкладке «Права ролей»; выдача ролей администратора и тех. администратора и сама таблица прав — всегда только у тех. администратора.

**Логин и пароль** есть только у администраторов. Администраторы входят **только** на `https://ДОМЕН/#admin`: логин, пароль и код из Google Authenticator (в обычном окне входа внизу ссылка «Вход для администраторов по логину»). По почте, телефону, коду и VK администратор не войдёт; «Забыли пароль?» по почте только задаёт новый пароль для входа по логину. У каждого администратора должен быть логин — выдаёт тех. администратор в карточке или `admin.sh`. Первых тех. администраторов заводят командой на сервере (нужен доступ по SSH), пароль вводится без показа на экране:
```
cd /srv/oche/app && sudo -u oche bash -c 'set -a; . /etc/oche.env; set +a; npm run admin -- new "Имя Фамилия" --login danil'
```
Остальные команды — так же, `npm run admin -- …`:

| Команда | Что делает |
|---|---|
| `list` | кто может входить по паролю, кто временно заблокирован |
| `new "Имя Фамилия" --login danil` | новый тех. администратор |
| `set OCH-1234 --login danil [--role tech\|admin]` | дать логин существующему игроку (ID из профиля) и роль |
| `password danil` | сменить пароль |
| `unlock danil` | снять блокировку после неверных паролей |
| `off danil` | убрать вход по паролю и закрыть его сеансы |
| `2fa-off danil` | сбросить двухфакторный вход (потерян телефон): сеансы закрываются, при входе — привязка заново |

Дальше логины администраторам (например, заказчику) тех. администратор выдаёт в панели: карточка игрока → «Вход по логину и паролю». Свой пароль каждый меняет во вкладке «Мой вход».

**Двухфакторный вход обязателен** для администраторов: после пароля — 6 цифр из Google Authenticator (подойдёт любое приложение с TOTP, например Яндекс Ключ). При первом входе страница показывает QR-код — приложение привязывается за минуту, и выдаются 8 одноразовых резервных кодов (на случай, если телефона нет под рукой; новые — в профиле, «Новые коды»). Потерян телефон — другой тех. администратор сбрасывает 2FA в карточке, или с сервера: `bash /srv/oche/app/deploy/admin.sh 2fa-off логин`. Если сменить `COOKIE_SECRET`, привязки перестанут читаться — их нужно сбросить так же. Время на сервере должно быть точным (`timedatectl` — NTP включён по умолчанию).

Защита: пароль от 10 символов, хранится только хэш (scrypt); неверные пароли — 5 на аккаунт с одного адреса за 15 минут, 30 на аккаунт за час; неверные коды 2FA — 5 за 15 минут; сеанс администратора — 30 дней. Все действия администраторов и ведущих пишутся в журнал (вкладка «Журнал»).

## Вход через VK ID

Нужен домен с HTTPS (раздел «С доменом и HTTPS» ниже): VK возвращает игрока только на доверенный адрес сайта, по IP-адресу вход через VK не настроить.

1. На id.vk.com создать веб-приложение.
2. Указать:
   - базовый домен — домен сайта;
   - доверенный redirect URL — `https://ДОМЕН/api/auth/vk/callback`;
   - доступ — только «Имя и фамилия».
3. ID приложения задать на сервере: `bash /srv/oche/app/deploy/set.sh VK_APP_ID=12345678`. На странице входа появится вкладка «VK ID», в профиле — «Привязать VK».

Страница отправляет на вход обычной ссылкой: `/api/auth/vk?return=/текущий/путь`.

## VPS (Ubuntu 24.04)

Для проверки хватит 1 vCPU / 1 ГБ / 10 ГБ (на маленьком сервере скрипт сам добавит подкачку 2 ГБ), для работы с игроками — 2 vCPU / 2–4 ГБ. Нужен **внешний IPv4-адрес**: без него сайт не открыть снаружи, а сервер не скачает пакеты и код. Репозиторий открытый — ключи для GitHub не нужны.

### Тест без домена — сайт по IP (один раз, от root)
```
ssh root@IP_СЕРВЕРА
curl -fsSLO https://raw.githubusercontent.com/Daniryy/NTK_Darts/main/deploy/setup.sh && bash setup.sh
```
Скрипт ставит nginx, PostgreSQL и Node 22, скачивает код, создаёт базу и `/etc/oche.env` со случайными паролями, запускает службу `oche`, включает брандмауэр (SSH и 80), ночные копии и проверку раз в 5 минут. По ходу спросит:
- заполнить ли демо-данными (игроки, турниры, матчи) — чтобы было что посмотреть;
- имя, логин и пароль тех. администратора — это вы.

В конце покажет адрес `http://IP_СЕРВЕРА`. Вход администратора — `http://IP_СЕРВЕРА/#admin` (логин, пароль, код из Google Authenticator); игрокам выдаёте коды в «Панели управления» → «+ Новый аккаунт», они входят по коду. Без домена не работают вход через VK и установка на экран телефона (нужен HTTPS); вход по телефону — когда подключён сервис звонков (выше).

Без вопросов (например, по SSH-скрипту): `DEMO=1 ADMIN_NAME="Имя Фамилия" ADMIN_LOGIN=danil ADMIN_PASSWORD='…' bash setup.sh`.

### С доменом и HTTPS
1. Купить домен, в DNS создать запись `A` на IP сервера, дождаться, пока она заработает (`ping домен` показывает IP).
2. Запустить тот же скрипт с доменом — на новом сервере или поверх теста (данные сохранятся, сменится только адрес):
```
DOMAIN=oche.ru EMAIL=you@mail.ru bash setup.sh
```
Скрипт получит сертификат HTTPS (certbot, продлевается сам) и откроет порт 443. После установки задать `VK_APP_ID`, `SMTP_*`, `SMS_*` и `TELEGRAM_*` через `deploy/set.sh`.

### Обновление
```
bash /srv/oche/app/deploy/deploy.sh
```
`git pull`, зависимости, миграции, перезапуск и проверка, что сервер отвечает. Безопасность обновления:
- **копия базы перед миграциями** — если в обновлении есть новые файлы `db/migrations`, сначала `backup.sh`; копия не создалась — обновление отменяется;
- **автооткат** — не прошли `npm ci` или миграция, или сервер не ответил на `/api/health` за 15 с — код возвращается на прежнюю версию и перезапускается, приходит оповещение; версия запоминается в `/srv/oche/update-bad`, и автообновление её пропускает до следующей (вручную `deploy.sh` всё равно попробует). Уже применённые миграции не откатываются — они пишутся так, чтобы прежний код с ними работал;
- **nginx из репозитория** — сайт в `/etc/nginx/sites-available/oche` подключает `deploy/nginx-app.conf` (пути, кэш, лимиты, заголовки безопасности из `deploy/nginx-headers.conf`); после обновления `deploy/nginx-sync.sh` проверяет `nginx -t` и перезагружает nginx. Сервер, поставленный раньше, переводится на это сам при ближайшей проверке автообновления (прежний конфиг — `oche.bak` рядом). Если в старом конфиге уже есть HTTPS от certbot — один раз перезапустите `DOMAIN=… EMAIL=… bash setup.sh`.

**Проверка в GitHub:** `.github/workflows/test.yml` гоняет `npm test` с PostgreSQL 16 на каждый push и pull request — в main должно попадать только то, что проходит тесты.

**Автообновление** — сервер раз в 5 минут сам проверяет ветку на GitHub и, если там новое, запускает `deploy.sh`:
```
bash /srv/oche/app/deploy/autoupdate.sh on       # включить (status — проверить, off — выключить, run — обновить сейчас)
journalctl -u oche-update -n 30                  # что было при последних проверках
```
Если обновление не удалось, приходит оповещение в Telegram (`TELEGRAM_*`), а сайт остаётся на прежней версии кода.

### Демо
Режим «Демо» (Настройки → Данные → «Демо») — **тот же сайт**, что и настоящий: страница ходит на демо-сервер `/demo/api/` — ту же программу с отдельной базой `oche_demo`, где заполнены игроки и турниры. Отличаются только данные: всё остальное (экраны, права, панель управления, счётчик, табло) точно такое же. Войти можно за любого — «Вход в демо» показывает игроков, ведущих и администраторов; пароли и коды не нужны. Почта, SMS, VK и оповещения в демо выключены. Данные и фото демо сбрасываются каждую ночь в 4:10.

Демо-сервер ставится сам при обновлении (`deploy/demo-sync.sh`): база `oche_demo`, настройки `/etc/oche-demo.env` (`DEMO=1`, порт 3001, свои папки фото), служба `oche-demo`, ночной сброс `/etc/cron.d/oche-demo`. Сбросить сейчас: `sudo -u oche bash -c 'set -a; . /etc/oche-demo.env; set +a; cd /srv/oche/app && node db/seed.js --reset' && systemctl restart oche-demo`. Если страница открыта без сервера (например, с GitHub Pages), «Демо» работает по-старому — в браузере.

### Демо-данные и администраторы
- `setup.sh` ставит сервер пустым; демо-данные — только `DEMO=1 bash setup.sh`. Посмотреть демо можно и без сервера: Настройки → «Демо в браузере».
- Убрать демо-данные с работающего сервера проще всего в панели: «Управление» → «Сервер» → «Очистить сервер…» (тех. администратор; сервер сам делает копию базы). Из консоли — `bash /srv/oche/app/deploy/clean.sh` (подтверждение — `yes`) — удаляет все турниры и матчи, клубы, баннеры и игроков, которые не могут войти сами; аккаунты с логином, почтой, телефоном или VK остаются, их рейтинг обнуляется. Перед очисткой делается копия базы в `/var/backups/oche`.
- Тех. администратор с логином и паролем: `bash /srv/oche/app/deploy/admin.sh new "Имя Фамилия" логин` (пароль вводится дважды без показа на экране, от 10 символов). Ещё: `password логин`, `list`, `unlock логин`, `off логин`.

Настройки nginx обновляются вместе с кодом (см. «Обновление»). Папки фото и документов создаёт `setup.sh`; на очень старом сервере: `mkdir -p /srv/oche/uploads /srv/oche/private && chown oche:oche /srv/oche/uploads /srv/oche/private && chmod 700 /srv/oche/private`.

**Лимиты nginx:** с одного IP до 100 запросов к `/api/` в секунду (всплеск до 500 — в зале весь Wi-Fi за одним адресом), до 60 открытых потоков табло; сверх — `429`. Плюс лимит самого сервера по устройству (`RATE_MAX`).

**Локаль базы:** `setup.sh` создаёт базу в UTF-8 с локалью `C.UTF-8` — тогда поиск без учёта регистра работает и для кириллицы. Если база создана иначе, сервер пишет предупреждение в журнал при старте.

### Обслуживание
- **Журнал:** `journalctl -u oche -f`.
- **Состояние:** `systemctl status oche`, `curl localhost:3000/api/health`.
- **Копии:** `/var/backups/oche/`, в 3:30. База (игроки, рейтинг, матчи, тарифы, журнал) — каждую ночь, хранится 14 дней; фото и документы званий — по воскресеньям, хранятся 3 последние. Перед очисткой сервера — всё сразу (`backup.sh --full`). Отчёт в `/var/log/oche-backup.log`.
- **Восстановление:**
  ```
  set -a; . /etc/oche.env; set +a
  systemctl stop oche
  pg_restore --clean --if-exists -d "$DATABASE_URL" /var/backups/oche/oche-ДАТА.dump
  tar -xzf /var/backups/oche/uploads-ДАТА.tgz -C /srv/oche   # фото
  systemctl start oche
  ```
  Проверьте восстановление хотя бы раз до первого турнира.
- **Оповещения в Telegram:** сервер не отвечает, диск заполнен больше чем на 85%, копия не создалась. Сообщение приходит один раз при поломке и один раз при восстановлении.
- Вдобавок включите резервное копирование в панели провайдера: копии в `/var/backups/oche` лежат на том же диске и не спасут, если пропадёт сам сервер.
- **Таблицы не растут без конца:** раз в 10 минут сервер удаляет истёкшие сеансы и коды, журнал SMS старше 2 суток и журнал действий старше года.

## Нагрузка
Прогон `tools/load.js` (Node и PostgreSQL на одной машине, Node на одном ядре). Турниры по 64 игрока, все матчи первого круга идут одновременно, каждый со своего телефона; каждый игрок раз в 30 с обновляет свой турнир; на каждый турнир открыто табло (поток счёта).

| Игроков | Матчей сразу | Подходов в с | Подход, мс (p50 / p95 / p99) | Счёт до табло, мс (p50 / p95) | Доставлено на табло | Node, % ядра / память | PostgreSQL, % ядра |
|---|---|---|---|---|---|---|---|
| 250 | 122 | 12 | 3 / 6 / 10 | 54 / 58 | 976 из 976 | 4% / 87 МБ | 1% |
| 1000 | 496 | 50 | 3 / 5 / 9 | 34 / 55 | 3968 из 3968 | 9% / 73 МБ | 5% |
| 2000 | 1000 | 100 | 3 / 5 / 12 | 33 / 54 | 8000 из 8000 | 17% / 174 МБ | <5% |
| 2000, подход раз в 3 с, 5 табло на турнир | 1000 | 333 | 3 / 7 / 20 | 34 / 55 | 66 580 из 66 580 | 28% / 180 МБ | 39% |

Обычно подход раз в 10 с на матч, 2 табло на турнир. Ошибок нет ни в одном прогоне. Сервера 2 vCPU / 4 ГБ хватает с большим запасом.

Ограничение частоты считается по устройству (`X-Device-Id`, у потока табло — `?d=`), а не по IP: в зале все телефоны в одном Wi-Fi выходят с одного адреса.

## Как устроено
- Страницу, `api.js`, `shared/bracket.js` и `shared/games.js` отдаёт nginx, остальные файлы репозитория наружу не видны. До Node доходит только `/api/`.
- Сетку, места и рейтинг сервер считает тем же модулем, что и страница. На демо-данных результаты совпадают полностью.
- Подходы проверяются при приёме:
  - верный игрок по очереди, остаток, допустимые очки, закрытие через дубль;
  - упражнения (набор очков, большой раунд, сектор, крикет, x01 с лимитом подходов) считает тот же движок `shared/games.js`, что и страница; ничья в леге решается событием `bull`;
  - дубли `seq` пропускаются, при пропуске сервер отвечает `409`;
  - пачка принимается целиком или не принимается совсем.
- Одну игру сетки и одну попытку квалификации нельзя начать дважды: это держат уникальные индексы в базе.
- Квалификация (формат NDL): результаты в `qual_results` — из счётчика или от организатора; после закрытия сетка строится частями по 8 мест, номера игроков — места квалификации.
- Мишени держатся за готовыми играми: после результата свободная мишень сразу переходит к следующей готовой игре (`assignBoards` в `shared/bracket.js`).
- Рейтинг пересчитывается после матча: новый результат сдвигает двоих игроков, отмена результата пересчитывает всё. Статистика игроков хранится готовой.
- Ответ `204` на опрос отдаётся по версии из памяти (живёт 2 с), без похода в базу.
- **Табло** (`/api/tournaments/:id/stream`) получает изменения через `LISTEN/NOTIFY` PostgreSQL. Уведомление уходит только после успешной записи и работает при любом числе процессов сервера.
- **Замер нагрузки** (48 матчей, 250 открытых табло, 15 подходов в секунду — примерно впятеро выше реального турнира на 100 игроков):
  - задержка до табло 60–70 мс, через nginx — около 50 мс;
  - ошибок 0;
  - Node — 7% одного ядра, PostgreSQL — 2,5%, память 100 МБ.
