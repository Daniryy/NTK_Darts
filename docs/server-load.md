# Oche: как держать нагрузку при большом числе игроков

Инструкция на будущее для перехода с localStorage на сервер (VPS: 2 vCPU, 4 ГБ, Node.js + PostgreSQL + nginx).
Цель: счёт актуален у всех, сервер загружен на несколько процентов, обрывы связи ничего не теряют.

---

## 1. Главные правила

1. **Подход отправляется сразу после ввода.** Ничего не копим и не ждём таймера.
2. **Ни один подход не теряется.** Сначала он сохраняется на телефоне, потом отправляется. При обрыве досылается сам.
3. **Зрители спрашивают «есть ли новое?»**, а не скачивают всё. Нет изменений — пустой ответ.
4. **Свёрнутая вкладка и погасший экран ничего не запрашивают.**
5. **Тяжёлое считаем редко.** Рейтинг пересчитывается после матча, а не на каждый запрос. Сетку по результатам строит браузер: функция `resolver()` уже есть.

---

## 2. Запись счёта (маркер или игрок, который ведёт счёт)

### Как отправлять
- Каждый подход — отдельное событие:
  `{ matchId, seq, leg, playerIdx, points, darts, bust, checkout, clientTime }`
  - `seq` — порядковый номер подхода в матче (1, 2, 3, …). Он защищает от дублей и пропусков.
  - Отмена подхода — тоже событие: `{ type: 'undo', seq }`. Историю не стираем, а добавляем отмену.
- Сервер отвечает `{ ok: true, version }`, где `version` — номер версии матча после записи.

### Очередь неотправленного (outbox)
1. Подход введён → сразу кладём событие в `localStorage['oche.outbox']` → показываем счёт на экране → пробуем отправить.
2. Сервер ответил `ok` → удаляем событие из очереди.
3. Ошибка или нет сети → событие остаётся в очереди. Повторяем через 1 → 2 → 5 → 10 → 30 с (не чаще).
4. Досылаем сразу при событиях `online` и `visibilitychange` (экран снова включили).
5. Отправляем строго по порядку `seq`, по одному. Следующий — только после `ok` предыдущего.
6. В шапке счётчика маленький индикатор: «не отправлено: 3», когда очередь не пустая. Игра при этом не блокируется.

### Что проверяет сервер
- **Повтор.** Событие с уже записанным `seq` — просто ответить `ok`, ничего не меняя. Так повторная отправка безопасна.
- **Пропуск.** Пришёл `seq` больше ожидаемого — ответить `409 { expectSeq }`. Клиент досылает недостающие из очереди.
- **Право писать.** Устройство отмечено маркером этого матча (см. ниже).
- **Правдоподобие.** Очки 0–180, нет «невозможных» сумм (163, 166, 169, 172, 173, 175, 176, 178, 179), закрытие только через дубль, если включён дубль.
- Запись подхода — **одна транзакция**: вставить событие и увеличить `matches.version`.

### Один матч — один маркер
- Кто нажал «Играть», тот берёт «замок» матча (`marker_device`, `marker_until`). Замок продлевается каждым подходом.
- Если другой телефон открывает тот же матч, он видит его только для просмотра, с кнопкой «Забрать ведение счёта» (с подтверждением).
- Так два телефона не пишут разный счёт одновременно.

## 3. Чтение (зрители, страница турнира, лента)

### Версии вместо полной загрузки
- У каждого матча и турнира есть число `version`, которое растёт при любом изменении.
- Запрос: `GET /api/matches/:id?since=42`
  - Изменений нет → `204 No Content`. Это пустой ответ, доли миллисекунды.
  - Есть изменения → только новые события после версии 42 и новая версия.
- Для турнира: `GET /api/tournaments/:id?since=17`. Отдаём только изменённые результаты матчей. Сетку, места и подписи браузер пересчитывает сам.
- Альтернатива или дополнение: заголовки `ETag` и `If-None-Match` → ответ `304 Not Modified`.

### Как часто обновлять

| Экран | Частота | Примечание |
|---|---|---|
| Счётчик у маркера | не опрашивает | он сам источник данных |
| Живой матч у зрителя | **10 с** (режим экономии — 30 с) | плюс адаптивность, см. ниже |
| Страница турнира: сетка, «можно играть» | 20–30 с | |
| Лента, рейтинг, профиль | без автообновления | свежие данные при открытии и по свайпу вниз |
| Вкладка свёрнута или экран погас | **0** | при возврате — сразу один запрос |
| Матч завершён | **0** | опрос этого матча прекращается |

**Адаптивный интервал.** Если два ответа подряд «ничего нового», интервал растёт: 10 → 15 → 20 → 30 с. Как только пришло изменение, он снова 10 с. Матч активный — обновления частые, пауза в игре — редкие.

**Разброс (jitter).** К интервалу добавляем случайные ±20%, чтобы 250 телефонов не стучались в одну и ту же секунду.

### Пример клиента
```js
let since = 0, delay = 10000, timer = null;
async function poll() {
  if (document.hidden) return;                       // свёрнуто — молчим
  try {
    const r = await fetch(`/api/matches/${id}?since=${since}`);
    if (r.status === 204) delay = Math.min(delay + 5000, 30000);
    else { const d = await r.json(); apply(d.events); since = d.version; delay = 10000;
           if (d.finished) return; }                 // матч закончен — опрос прекращаем
  } catch (e) { delay = Math.min(delay * 2, 60000); } // нет сети — реже
  timer = setTimeout(poll, delay * (0.8 + Math.random() * 0.4));
}
document.addEventListener('visibilitychange', () => { if (!document.hidden) { clearTimeout(timer); poll(); } });
```

## 4. Сервер

- **nginx:** раздаёт статику (`index.html`, шрифты, иконки) сам, с `gzip` и кэшем. До Node доходят только `/api/*`. Включить `keepalive`.
- **Node.js:** 2 процесса (pm2 или cluster), по одному на ядро. Автоперезапуск при падении и после перезагрузки сервера.
- **PostgreSQL:** пул соединений 10–20 на весь сервер. Индексы:
  - `match_events (match_id, seq)` — уникальный;
  - `matches (tournament_id)`, `matches (version)`;
  - `tournaments (status)`.
- **Кэш в памяти:** текущая версия каждого активного матча и турнира. Ответ `204` отдаётся без похода в базу.
- **Рейтинг и статистика игрока** пересчитываются один раз, когда матч завершён. Результат хранится в таблице, а не считается при каждом открытии профиля.
- **Ограничение частоты** (rate limit) на `/api`: например, не больше 5 запросов в секунду с одного устройства. Защита от зависших или кривых клиентов.
- **Ответы маленькие:** только нужные поля, без истории всех матчей.

---

## 5. Когда нужно «мгновенно»

Опроса раз в 10 с хватит для старта и для сотен зрителей. Мгновенное обновление (SSE или WebSocket) стоит делать, когда:
- появится большое табло в клубе или трансляция, где важна каждая секунда;
- зрителей станет больше 1 000 одновременно.

SSE проще: одно соединение на зрителя, сервер сам присылает новые подходы. На VPS это работает, на обычном хостинге — нет.

## 6. Проверка перед большим турниром

1. **Нагрузочный тест** (k6 или autocannon). Сценарий: N маркеров отправляют подход раз в 30 с, 10% зрителей опрашивают матч раз в 10 с. Прогнать для 250, 500, 1 000 и 2 000 игроков. Смотреть время ответа (цель — p95 < 200 мс) и загрузку CPU (цель — < 50%).
2. **Тест обрыва связи:** выключить сеть на телефоне маркера на 2 минуты, ввести 5 подходов, включить сеть. Все 5 должны появиться у зрителей в правильном порядке, без дублей.
3. **Тест двух телефонов** на один матч: второй должен получить режим просмотра.
4. **Резервные копии:** ежедневный `pg_dump` плюс резервное копирование в панели провайдера. Хотя бы раз проверить восстановление.
5. **Мониторинг:** загрузка CPU и памяти, место на диске, число ошибок `/api` за 5 минут. Оповещение в Telegram, если что-то не так.

---

## 7. Ориентиры (2 vCPU / 4 ГБ)

- Нагрузка: игрок ≈ 0,1 запроса/с, зритель ≈ 0,1–0,15 запроса/с.
- 250 игроков + 25 зрителей ≈ 30 запросов/с — это 5–10% сервера.
- Комфортно: около 1 000–1 500 игроков и 10% зрителей. Потолок — около 3 000 игроков.
- Узкое место на практике — Wi-Fi или мобильная связь в клубе, а не сервер. Отсюда очередь неотправленного (раздел 2).

## Чек-лист

- [ ] Подход отправляется сразу, через очередь `outbox` в localStorage
- [ ] У событий есть `seq`, сервер игнорирует дубли и просит недостающие
- [ ] Один маркер на матч (замок), остальные смотрят
- [ ] Версии у матчей и турниров, ответ `204`, когда ничего не изменилось
- [ ] Опрос: матч 10 с (адаптивно до 30 с), турнир 20–30 с, лента без автообновления
- [ ] Пауза при свёрнутой вкладке, остановка после конца матча, разброс ±20%
- [ ] Индикатор «не отправлено: N» и досылка при `online` и `visibilitychange`
- [ ] nginx раздаёт статику, Node — 2 процесса, пул PostgreSQL, индексы
- [ ] Кэш версий в памяти, рейтинг считается после матча
- [ ] Rate limit на `/api`
- [ ] Нагрузочный тест, тест обрыва связи, бэкапы, мониторинг
